Leak 1 — Long stack frame keeps local variable alive heap-only Leak1_long_frame.hprof

heap total: 155 MB top retainer: 100 MB retainer class: victor.training.performance.leak.obj.Big100MB

Heap evidence

  • Top retainer is a single Big100MB instance (retained 104,857,664 B) wrapping a single int[1_000_000].
  • referrers() on the Big100MB returns empty — no heap object refers to it.

Root cause

An object with no heap referrer that is still in the dump must be rooted as a Java Local on a thread's stack frame. A method allocated Big100MB as a local variable and is currently still on the stack (likely sleeping, blocking on I/O, or in a long-running loop). While that frame exists, the local stays a GC root.

Fix: reduce the lifetime of the local — process & release the big object before the long-running operation, or null out the reference once you are done with it.

Leak 2 — Three “hidden links” pinning enclosing instances heap-only Leak2_hiddenLinks_all3.hprof

heap total: 113 MB top retainer: 20 MB × ~4 retainer classes: CalculatorFactory$1, CalculatorFactory$2, CalculatorFactory$Calculator, ReferencePipeline$2

Heap evidence

  • CalculatorFactory$1 — anonymous inner class. Field this$0 → CalculatorFactory (which owns a Big20MB).
  • CalculatorFactory$2 — anonymous subclass of HashMap (double-brace init pattern). Same this$0 backlink.
  • CalculatorFactory$Calculator — non-static inner class. Same this$0 backlink.
  • java.util.stream.ReferencePipeline$2 — a Stream pipeline retaining its source, capturing the enclosing factory.

Root cause

All four are silent compiler-generated references to an enclosing object the developer did not realise they were creating: anonymous classes, double-brace init, non-static inner classes, and streams returned from a method. Each surviving instance keeps its 20 MB enclosing factory alive.

Fix: make inner classes static; avoid the new HashMap() {{ put(...); }} idiom; do not return live Streams from methods whose state should die with them.

Leak 3 — ArrayList.subList() pins the whole parent list heap-only Leak3_SubList.hprof

heap total: 73 MB top retainer: 11.7 MB retainer: Leak3_SubList.lastTen → ArrayList$SubList

Heap evidence

Leak3_SubList
   └─ lastTen: ArrayList$SubList   { size = 10, offset = 49991, modCount = 50001 }
                └─ root: ArrayList { size = 50001 }
                          └─ elementData: Object[] (9.5 MB)

Root cause

A field named lastTen holds the result of list.subList(list.size() - 10, list.size()). The SubList is a view over the original 50,001-element ArrayList — it stores a reference to the parent (root) and just an offset/size window. So caching the "last 10" prevented GC of all 50,001 elements.

Fix: new ArrayList<>(list.subList(...)) to copy out and release the parent.

Leak 4 — XML DOM trees retained via Xerces deferred nodes heap-only Leak4_XML_DOM.hprof

heap total: 85 MB top retainer: 34 MB retainer: java.util.ArrayList (size = 1000)

Heap evidence — class histogram

  • com.sun.org.apache.xerces.internal.dom.DeferredTextImpl × 127,000
  • com.sun.org.apache.xerces.internal.dom.DeferredElementImpl × 62,000
  • com.sun.org.apache.xerces.internal.dom.AttributeMap × 62,000
  • An ArrayList of 1,000 fragments retains 34 MB of DOM nodes.

Root cause

Xerces DOM Nodes each hold an ownerDocument pointer back to the root Document. Storing any node from a parsed DOM in a collection therefore pins the entire document subtree.

Fix: extract the primitive data you need (Strings, numbers) before letting the parsed tree go out of scope; or use a streaming parser (SAX/StAX) for large inputs.

Leak 5 — ThreadLocal in a thread pool heap-only Leak5-ThreadLocal+ThreadPool.hprof

heap total: 260 MB top retainers: 10 × ~20 MB Tomcat workers retainer class: org.apache.tomcat.util.threads.TaskThread

Heap evidence

  • Top 10 retainers in biggest_objects are TaskThread instances, each retaining ≈20 MB.
  • Below them: many java.lang.ThreadLocal$ThreadLocalMap / ...Entry[] structures, each ≈20 MB.

Root cause

A ThreadLocal<Big20MB> was populated in a request thread and never remove()d. Because Tomcat reuses pool threads across requests, the entry sits in the worker's ThreadLocalMap until the thread itself dies (i.e., never). Effect: pool-size × ThreadLocal-payload of permanently retained heap.

Fix: always call threadLocal.remove() in a finally (or use a filter/interceptor); for request-scoped data prefer RequestContextHolder or Spring's request scope.

Leak 6 — ForkJoinPool.commonPool() backlog heap-only Leak6_AsyncFJPCommonPool.hprof

heap total: 408 MB top retainer: ~42 MB in a single FJP WorkQueue retainer: ForkJoinPool$WorkQueue[] + many CompletableFuture$AsyncRun (~10 MB each)

Heap evidence

  • A ForkJoinPool$WorkQueue[] retains ~42 MB.
  • Each WorkQueue contains a ForkJoinTask[] retaining 20–30 MB.
  • The queued tasks are CompletableFuture$AsyncRun instances, each retaining ≈10 MB.

Root cause

Code uses CompletableFuture.runAsync(...) / supplyAsync(...) without passing an executor, which defaults to the common ForkJoinPool. Each task's closure captures a ~10 MB blob. Requests outrun consumption, the queue fills up, and every queued task holds its captured data.

Fix: always pass a bounded, dedicated Executor to supplyAsync/runAsync; control concurrency at the source so the queue cannot grow unboundedly.

Leak 7 — Unbounded thread creation heap-only Leak7_ThreadLeak.hprof

heap total: 71 MB thread count: 1,743 java.lang.Thread instances

Heap evidence — class histogram

  • java.lang.Thread — 1,743 instances
  • jdk.internal.misc.InnocuousThread — 79
  • org.apache.tomcat.util.threads.TaskThread — 202

Root cause

A typical Spring Boot app has 30–60 threads. 1,700+ live Thread instances mean code is creating threads per request or per task without bounds — either new Thread(...).start() or an executor with Integer.MAX_VALUE maximum pool size. Each thread costs ~1 MB of stack (off-heap) plus its heap-resident state; under load this leads to OutOfMemoryError: unable to create new native thread.

Fix: reuse threads via a bounded ThreadPoolExecutor; cap maximumPoolSize; use virtual threads where appropriate.

Leak 8 — Tomcat thread-pool deadlock heap-only Leak8_deadlock_all_Tomcat.hprof

heap total: 71 MB no large retainer thread count: 202 TaskThread + 202 WrappingRunnable

Heap evidence

  • No top retainer exceeds 5 MB — this is not a memory leak in the usual sense.
  • Tomcat's worker pool is at its default ceiling (200) and every thread has an active wrapping runnable: every worker is busy / blocked.

Root cause

All Tomcat worker threads are blocked, so the server cannot accept new work — symptoms look like a memory problem but the cause is thread starvation. Common triggers: a handler that itself calls back into the same server over HTTP and waits for the response (self-deadlock), a shared synchronized lock contention, or a long blocking I/O call without timeouts.

Diagnosis next step: a thread dump (jstack) would show the exact monitor / lock each worker is waiting on — that information is not present in the heap dump.

Leak 10 — Shutdown hooks pin big closures forever heap-only Leak10_ShutdownHooks.hprof

heap total: 155 MB top retainer: ~104 MB on a java.lang.Class static retainer: IdentityHashMap → 5 Threads → OldLib$$Lambda

Heap evidence

  • A java.lang.Class holds a static IdentityHashMap retaining 104 MB → this is java.lang.ApplicationShutdownHooks.hooks.
  • The map contains 5 Thread instances, each retaining ~20 MB.
  • Each thread's target is an OldLib$$Lambda capturing a 20 MB payload.

Root cause

Every call to Runtime.getRuntime().addShutdownHook(thread) registers the thread (and everything it transitively references) in the JVM's static map. Once added, the hook can never be GC'd — it must remain reachable so the JVM can run it on shutdown. Five lambda-carrying threads × 20 MB closures = 100 MB pinned for the JVM's lifetime.

Fix: use removeShutdownHook when you no longer need it; or design the hook to be a tiny lookup (e.g., look up a service via DI) rather than capturing big state in its closure.

Leak 11 — Unbounded idempotency-key store heap-only Leak11_IdempotencyFilter.hprof

heap total: 135 MB top retainer: 61.6 MB retainer chain: IdempotencyFilter → SynchronizedSet → HashSet → HashMap (399,975 entries)

Heap evidence

IdempotencyFilter
   └─ Collections.SynchronizedSet
        └─ HashSet
             └─ HashMap   { size = 399 975, modCount = 399 975 }
                  └─ Node[]   (61.6 MB)

Root cause

A filter that records request idempotency keys into a process-local Set that grows monotonically — there is no eviction (no TTL, no LRU, no external store). After ~400k requests the set is 60 MB, then 120 MB, then OOM.

Fix: bound the cache (Caffeine, Guava with maximumSize + expireAfterWrite) or move idempotency to an external store (Redis) with TTL.

Leak 13 — Hibernate Session L1-cache OOME heap-only Leak13_Hibernate_OOME.hprof

heap total: 512 MB top retainer: 471 MB retainer: org.hibernate.engine.internal.StatefulPersistenceContext

Heap evidence

  • A single StatefulPersistenceContext retains 471 MB — that is 92 % of the entire heap.

Root cause

StatefulPersistenceContext is Hibernate's first-level cache — every entity loaded by a Session is kept there until the Session/EntityManager is closed or clear()'d. A long-running transaction loaded a very large result set (findAll() on a huge table, or naïve pagination by iterating all rows) and never released the entities.

Fix: use streaming queries with EntityManager.clear() every batch; use Stateless­Session for bulk reads; project to DTOs (select new ...) so JPA doesn't add to the L1 cache.

Leak 14a — Classloader pinned by a surviving instance heap-only Leak14_ClassLoader-instanceRef.hprof

heap total: 178 MB top retainers: 6 × ~20 MB java.lang.Class objects retainer: java.net.URLClassLoader × 7 + int[1_000_000] statics

Heap evidence

  • 7 URLClassLoader instances are alive.
  • 6 java.lang.Class objects (one per plugin class) each retain ≈20 MB — a static field of int[1_000_000] per class.

Root cause

The app loads plugin JARs into private URLClassLoaders and discards the loader when the plugin is unloaded. A ClassLoader is only GC-eligible when every instance of every class it defined is unreachable — because each instance silently holds its .getClass().getClassLoader(). A single surviving instance is enough to anchor the entire classloader (and all its statics) in memory.

Fix: on plugin unload, audit any caches, listeners, or references that may still hold plugin-class instances; use weak references for plugin-supplied callbacks.

Leak 14b — Classloader pinned by an un-cancelled Timer heap-only Leak14_ClassLoader-thread.hprof

heap total: 157 MB top retainers: 5 × ~20 MB java.lang.Class retainer: 6 URLClassLoader + 5 java.util.TimerThread

Heap evidence

  • 6 alive URLClassLoader instances.
  • 5 java.util.TimerThread instances still running — one per "unloaded" plugin.

Root cause

Each plugin started a java.util.Timer in its initializer and never called timer.cancel() on shutdown. The resulting TimerThread keeps running and carries the plugin's contextClassLoader as a field — so the plugin's URLClassLoader can never be collected.

Fix: always pair new Timer() with timer.cancel() in a teardown hook; better, use ScheduledExecutorService with explicit lifecycle and daemon threads.

Leak 16 — GUI observer never deregistered heap-only Leak16_GuiObserver.hprof

heap total: 643 MB top retainer: 6 × ~105 MB retainer: Leak16_GuiObserver$LeakyFrame (extends JFrame)

Heap evidence

  • Six instances of LeakyFrame survive — each holds a big: Big100MB field.
  • Each LeakyFrame's visible flag is false — the windows were closed/disposed, yet they remain reachable.

Root cause

The disposed-but-retained JFrames are still subscribed to some long-lived "subject" (a model, a service, or Swing's per-AppContext event bus) via the observer pattern. The publisher's listener list keeps strong references to the frames; dispose() does not deregister them. Result: every "closed" window plus its 100 MB payload sticks around forever.

Fix: deregister listeners in windowClosing/dispose(); or expose only weak listener references on the subject side (e.g., WeakListenerList, Guava EventBus with weak subscribers).
